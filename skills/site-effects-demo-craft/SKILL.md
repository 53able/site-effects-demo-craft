# 既存サイトの演出とデモ制作

元サイトの個性を保ち、描いている過程を気持ちよく見せる。演出の豊かさ、見やすさ、待ちの短さを実物で判断する。

## 標準の実行経路

標準は、ユーザーが編集できるサイトへ演出を組み込み、そのサイトをローカルで起動する。参照URLは見た目・動きの調査に使い、外部サイトを無断で複製したり本番を書き換えたりしない。新しい明示指示を優先する。

1. 対象プロジェクトの構成、起動方法、公開ディレクトリ、既存効果を確認する。録画のみの依頼なら導入・改修をせず、既存の挙動を撮る。効果以外のデザインを変えない。
2. スキルの実際の配置場所を`SKILL_DIR`、対象プロジェクトを`APP_DIR`に設定し、同梱の実行ファイルを導入する。スキル自身や他の無関係なディレクトリを出力先にしない。

   ```sh
   node "$SKILL_DIR/scripts/install-local.mjs" --project "$APP_DIR"
   ```

3. 対象ページで`/swarm-demo/swarm-build.js`、次に`/swarm-demo/swarm-demo.js`を読み込み、DOMの準備後に`window.SwarmDemo.start()`を呼ぶ。フレームワークのクライアント側で順序を守り、アンマウント時は`destroy()`する。実際のAPIと確認手順は[ローカル導入](references/local-integration.md)を読む。導入しただけで描画済みと報告しない。
4. 写真・見出し・ボタン等へ`data-swarm-block`を付ける。自動抽出は初期値として使い、親に含まれるだけで細分化完了にしない。役割・配色・緊急度を確認し、必要なセレクタを調整する。
5. canvas-uiの適用では、React 19の対象アプリへ公式コンポーネントとそのライセンスを直接取得する。

   ```sh
   node "$SKILL_DIR/scripts/install-canvas-ui.mjs" --project "$APP_DIR"
   ```

   取得した依存一覧を対象アプリで確認し、不足分を導入する。生成した`CanvasUiEffect`をサイズのある既存の枠内へマウントし、利用する権利のある画像とサイトの色を渡す。依存の追加やファイル取得だけで「canvas-uiを適用した」と報告しない。React 19以外は自動移行せず、対象に合う公式経路を確認する。通常の組み込み依頼でcanvas-uiを黙って省略しない。
6. 対象アプリの通常の方法でローカル起動し、Swarmのカーソル・描画、canvas-uiの描画、元デザインの維持を実ブラウザで確認する。Replay、Finish、破棄、上下スクロール、可視対象の完成を確かめる。URL、実行コマンド、確認結果と不足を共有する。WebGL非対応のフォールバックは、ネイティブ効果の成功と区別する。

同梱エンジンはMITで配布する2D版。canvas-ui由来のHTMLキャプチャ・3D飛来実装は含まない。canvas-uiの実装は利用先アプリへ取得する別ライセンスの依存であり、スキルのMITで再ライセンスしない。ソースの再配布を含むライセンス通知は保持する。一般の動画編集や開発エージェントの編成へ範囲を広げない。

## 演出を改善する判断基準

**元のデザインと配色を守る。** 演出改善の名目で背景、書体、コピー、余白、レイアウトを変えない。効果を切った状態と完成後を元ページと比べ、意図しない差を確認する。色はサイトの配色に合わせる。高級感を黒背景や金色への変更と同一視しない。

**材質は出力サイズで見せる。** 金属感を求められた場合は反射、輪郭、ハイライト、面の質感を検討する。拡大した静止画だけで評価せず、実際の動画表示サイズと動きの中で見えるか、明暗の背景で読めるかを確認する。金属表現自体を全サイトに必須にしない。

**意味のある単位まで描く。** 組み上げ型の演出では見出し、写真、画像、ボタン、リンクなどを個別の視覚単位として扱う。写真が複数あるカードを親カードの一括表示だけで済ませない。「すべて描く」の確認では対象の取りこぼしと粒度を別に見る。親ブロックの中に含まれるだけでは細分化の証拠にならない。DOM全ノードや単語ごとの分割、特定の要素数を目標にしない。

**描いている過程を画面内で見せる。** 組み上げを見せる用途では、画面外で先に描き終える高速化を避ける。資産準備、計算、描画を伴わない移動の前倒しは、実際の描画開始と区別して使う。親子の依存がある場合、親完成前に子を描いて順序を崩さない。

**見切れの緊急度を扱う。** スクロール方向の出口に近い可視要素を先に描く。下向きなら上端、上向きなら下端から消えそうな要素を見る。距離や担当役割だけを優先して未完成の要素を見切れさせない。同程度の緊急度なら移動距離や役割を使って段取りを整える。

**待ちの原因を減らす。** 人数増や一律の速度変更だけで解決せず、移動、親子待ち、小要素の所要時間、役割配分、固定待機のどこで止まるか調べる。描画を見せる時間を残して前倒しや時間配分を比較する。人数増も実測で選べるが、人数そのものを成果にしない。

**安定した動きにする。** 名札の位置飛び、濃さの点滅、重なり回避の往復、大きな枠の急伸を遷移中に確認する。位置選択と移動・濃さの変化を安定させ、読める状態を保つ。違和感の指摘から、あらゆる揺れ演出を禁止する仕様を推定しない。

**3Dは目的と比較で選ぶ。** 技術が使えることだけを採用理由にしない。既定ではページ全体を俯瞰へ傾けない。局所3Dを明示されたら、その範囲で見やすさ、着地の連続性、効果のない場合との違いを確認する。過去の2D採用を将来の3D禁止にしない。

Swarm型のカーソル、役割割当、描画順、親子関係や待ち時間を扱うときは、[Swarm型の調整パターン](references/swarm-patterns.md)を読む。一般の演出にカーソルや役割を追加するための指示ではない。画面上のエージェント表現と、実際の開発エージェントの編成を区別する。

## デモ録画と納品

- 組み上げを見せる録画では、画面内の対象が完成してから短く保持し、次へ滑らかにスクロールする。固定秒数だけに頼らず完了状態と同期する。時間切れを完成扱いにせず、未完了・見切れを記録する。
- 代表的な録画シナリオで、未完成のまま画面外へ出る対象が0になることを確認する。この録画制御を通常サイトの手動スクロールの強制停止へ広げない。手動操作での見切れは条件を記録して改善し、あらゆる操作に対する0保証をしない。
- デモ納品は、指定がなければ同じキャプチャから字幕あり・なしの両版を用意する。字幕なしだけを求められた場合は、その版を先に提示する。字幕なし版に注釈が残っていないか実物を確認する。
- 原キャプチャと各出力のfps、尺、フレーム数、内容の対応を確認する。両出力同士が一致するだけでは原映像からの欠落がない証拠にならない。差があれば程度と影響を説明する。
- 書き出しfps、動画内のコマ落ち・重複、実ブラウザでのフレーム時間や滑らかさを別々に判断する。仮想時計で1コマずつ作った動画を、リアルタイム実行性能の証明にしない。
- 完成動画が用意できたら、残る検証と区別して速やかに実ファイルを共有する。確認した条件と未確認の項目を短く添え、動画がない状態を説明文や静止画だけで納品済みにしない。

## 確認の終点

変更した効果について、完成画面の維持、描画単位、遷移中の見え方、待ちと見切れを依頼に応じて確認する。録画依頼では実際の出力と納品版を確認する。実装を変えた場合は変更に合う既存テストやブラウザ確認を使う。判断だけの評価と、実ブラウザ・実動画で確認した結果を分け、未検証の品質を合格扱いにしない。
